Роль: Senior Full-Stack Web Developer.

Задача: Разработать легковесную веб-систему тайм-трекинга для сотрудников. 

Технологический стек (рекомендуемый):

Frontend: HTML5, CSS3 (с упором на мобильную верстку), чистый JavaScript (ES6+). Использование тяжелых фреймворков (React, Vue) запрещено, если это не оправдано простотой решения.
Backend: Node.js (Express.js) или Python (FastAPI/Flask).
База данных: SQLite (файл data.db) — для быстрого старта и простоты деплоя. 
Альтернатива (если выбрано сохранение в Google Sheets): Node.js + Google Sheets API v4.

Архитектура и безопасность (критически важно):

Аутентификация: Система должна иметь страницу входа. При первом запуске создается аккаунт администратора (руководителя). Пароли хранятся в базе в виде соленого хеша (использовать библиотеку bcrypt).
Роли: Существует две роли: admin (руководитель) и user (сотрудник). 
Изоляция данных: Сотрудник (user) после авторизации видит только свои записи. В URL или параметрах запросов нет возможности подменить ID пользователя. Руководитель (admin) видит записи всех сотрудников.
Сессии: Использовать httpOnly куки для хранения JWT-токена или ID сессии.
Функциональные требования

1. Интерфейс для сотрудника (мобильный приоритет)

Главная страница после входа: большая кнопка «Начать работу» и список своих незавершенных записей за сегодня.
Если таймер не запущен — форма ручного ввода:
Дата: <input type="date"> (по умолчанию сегодня).
Проект: <select> (выпадающий список из справочника).
Задача / работа: <input type="text">.
Время начала: <input type="time">.
Время окончания: <input type="time">.
Перерыв (минуты): <input type="number" min="0">.
Примечания: <textarea>.
Кнопка «Сохранить». 
Валидация на клиенте: время окончания должно быть позже времени начала.
Адаптивность: интерфейс должен быть удобен для ввода одной рукой на смартфоне. Крупные поля, отсутствие горизонтальной прокрутки.

2. Интерфейс для руководителя (Admin Dashboard)

Таблица со всеми записями всех сотрудников.
Столбцы: ФИО, Дата, Проект, Задача, Начало, Конец, Перерыв (мин), Длительность (часы, формат 1.50), Примечания.
Длительность рассчитывается по формуле: (Время_окончания - Время_начала) - (Перерыв / 60). Результат округлять до двух знаков.
Фильтры над таблицей: по дате (диапазон), по сотруднику, по проекту.
Сортировка по любому столбцу (стрелочки в хедере таблицы).
Поле «Ставка (руб/час)» в профиле каждого сотрудника.
Автоматический подсчет «Итого к оплате» для отфильтрованных записей: Длительность × Ставка. Сумма должна отображаться внизу таблицы.
Кнопка экспорта текущей выборки в CSV.

3. Справочники

Админка для руководителя: управление списком «Проектов» (добавить, редактировать, деактивировать) и списком «Сотрудники» (ФИО, роль, ставка). Удаление сотрудников запрещено (только деактивация), чтобы не ломать старые записи.

4. Логика автоматического расчёта (Backend)

При сохранении записи сервер должен пересчитывать длительность в часах. 
Обработка перехода через полночь: если время окончания меньше времени начала (например, 22:00 – 02:00), считать, что работа закончилась на следующий день.
Интеграция с Google Sheets (Опционально, на выбор исполнителя)

Если реализация через базу данных покажется излишней, используй Google Sheets как основное хранилище.

Структура таблицы: Лист Records (ID, Timestamp, UserID, Date, Project, Task, Start, End, BreakMin, Notes, DurationHours). Лист Users (UserID, Name, Role, Rate, PasswordHash). Лист Projects (ProjectID, Name, IsActive).
Аутентификация: Использовать сервисный аккаунт Google Cloud. Файл credentials.json должен добавляться в .gitignore.
Библиотека: googleapis (Node.js) или gspread (Python).
Чтение: Для админ-панели данные запрашиваются из Sheets, парсятся и отдаются на фронтенд как JSON.
Запись: При добавлении новой записи сотрудником, бэкенд дописывает строку в конец листа Records.
Ограничения и нефункциональные требования
Код должен быть чистым, прокомментированным, с понятными именами переменных.
Обязательно наличие файла .env.example с перечнем переменных (секреты, ключи).
Отсутствие внешних UI-фреймворков вроде Bootstrap. Допускается использование небольшого CSS-ресета или написание простых стилей с нуля (Mobile-first).
Защита от SQL-инъекций (использовать параметризованные запросы) и XSS (экранировать вывод на фронтенде).
Обработка ошибок: если Google API недоступен, пользователь должен видеть понятное сообщение, а не технический краш.
